## 1. Хранение и модель данных (этап 1) — ✅

**Файлы:** `lib/db/` (tables.dart, app_database.dart, fts_schema.dart),
`lib/data/`, `lib/domain/`.

- Схема v2: 16 таблиц — базовые сущности §3 (Folder, Note, TaskList, Task,
  Tag, EntityTag, RecurrenceRule, TaskOccurrence, Reminder, Conflict) и
  служебные (OutboxEntries, SyncState, DeletionMarkers, DeviceSettings,
  SharedSettings, SyncBase).
- Общие колонки синхронизации (`SyncColumns`): revision, base_revision,
  modified_at, device_id, deleted_at (soft delete §11).
- Постоянные UUID; срок как DueSpec (kind + `yyyy-MM-dd` + минуты дня) —
  отсутствие времени не кодируется как UTC-полночь (§3).
- FK включены, миграция v1→v2 (добавление sync_base) с сохранением данных,
  WAL/synchronous, тяжёлые запросы в фоновом isolate, база в приватной
  области данных (§2).
- FTS5 + unicode61: notes_fts (title+текст Delta), tasks_fts (text+
  description), поддержка триггерами, безопасный разбор пользовательского
  ввода в MATCH (§2; морфология не обещается).
- Индексы: list+parent, due, completed, priority, series, folder+pin,
  modified, tag-связи.
- Сервисы: NotesService (создание/контент/закрепление/перенос/корзина),
  TasksService (дерево в одном списке, запрет циклов, перенос ветки целиком,
  reorder, подтверждение ветки), TaskListsService (Входящие, embed,
  перенос между заметками, сортировки), TagsService, FoldersService,
  TrashService (30 дней, restore, purge → DeletionMarkers), SearchService
  (фильтры §4), SettingsService, OutboxLedger.
- Правила времени: `lib/domain/time_rules.dart` — граница просрочки даты
  по следующей полуночи, окно 48 часов, неделя Пн–Вс, несуществующие числа
  месяца (31 янв → 28/29 фев), DST-скачок и повторяющееся время (первое
  вхождение), перенос сроков подзадач по календарной разнице.
- Сортировка списков: `lib/domain/task_sort.dart` — по сроку (без срока
  внизу) и по приоритету с ручным порядком как последним критерием (§4).

## 3. Вход и синхронизация (этап 3) — ✅

**Файлы:** `lib/cloud/` (firebase_config.dart, firebase_rest.dart),
`lib/auth/` (auth_service.dart, google_oauth_desktop.dart, secure_store.dart),
`lib/sync/` (sync_engine.dart, sync_mapper.dart, sync_merge.dart),
`firestore.rules`, `docs/cloud-setup.md`.

- **Вход Android**: Credential Manager через google_sign_in 7.2
  (serverClientId = Web-клиент, nonce) → id_token.
- **Вход Windows**: системный браузер, OAuth Authorization Code + PKCE
  S256, случайные state/nonce, loopback 127.0.0.1 на свободном порту,
  Desktop-клиент; проверка nonce и state; клиент secret — публичное
  значение installed-app (§9), требует Google при обмене кода.
- **Обмен на Firebase**: accounts:signInWithIdp (пост-боди `id_token`,
  fallback `access_token`); refresh через securetoken; токены в
  EncryptedSharedPreferences (Keystore) / DPAPI (FFI win32) — собственная
  реализация вместо flutter_secure_storage (не требует ATL в CI).
- Один Google-аккаунт → один Firebase UID на обеих платформах (проверено:
  UID `2fANE…iBL93` совпал).
- **Правила**: `firestore.rules` — владелец по UID (двойная сверка:
  workspace-путь + вшитый UID), валидация формы workspace- и entity-
  документов (набор полей протокола, целые неотрицательные счётчики);
  вне workspaces — deny by default.
- **Протокол §10**:
  - мутация + outbox — одна транзакция (все сервисы);
  - push: beginTransaction → чтение workspace → commit_seq+1 → пакет
    entity-записей с этим seq → commit с precondition по updateTime;
    повтор при ABORTED;
  - защита повторного push: `:batchGet` в транзакции, upsert применяется
    при `op.revision >= cloud.revision`, delete — по правилу позднего
    действия; stale-операции пропускаются; `last_op_id` в документе;
  - pull: курсор только после локальной транзакции; курсор не двигается
    push'ем (чужие промежуточные seq не теряются); страницы по 300;
  - epoch: push пишет в активный epoch локального состояния; смена epoch
    сервером останавливает синхронизацию и требует явного подтверждения
    с JSON-бэкапом несинхронизированного;
  - workspace привязан к аккаунту до любого сетевого запроса; чужой
    аккаунт не унаследует копию (§9);
  - автослияние: 3-way по sync_base (последняя общая подтверждённая база),
    независимые поля объединяются, пересечения → Conflicts; удаление vs
    редактирование — позднее действие, при равенстве удаление;
  - разрешение конфликта — с проверкой ревизии, синхронизируется.
- **Первый вход**: pull-first (облачные версии применяются слиянием до
  отправки локальных), затем локальные сущности в outbox и push (§9).
- **Выход**: вопрос о локальной копии; предупреждение о несинхронизированном
  перед удалением; облако не удаляется; rebootstrap Входящих (§9).
- Интервалы: немедленно при старте/входе, 30 с при открытом приложении,
  ручная кнопка; ошибки сети/квот/доступа видны в UI и журнале (§10).
- Гонка создания workspace: 409 → перечитать и продолжить.
- Безопасный разбор не-JSON ответов REST; классификация ошибок по HTTP и
  gRPC-статусу (PERMISSION_DENIED/ABORTED/RESOURCE_EXHAUSTED).

- Dashboard: логика предков и индикаторов внимания — этап 4.
- Background-синхронизация (WorkManager), напоминания, виджет, трей —
  этап 5.
- Экспорт/импорт, replace-протокол — этап 6.
- CI/Releases, релизная подпись, обновлятор — этап 7 (нужны keystore и
  SHA-1 релизного ключа от владельца).
