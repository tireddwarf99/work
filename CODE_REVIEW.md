### Firestore Rules: оценка для личного аккаунта

Текущий [firestore.rules](firestore.rules) для личного приложения ограничивает
доступ workspace UID из пути и одним закреплённым Firebase UID
`2fANEOpUDmczCaVAhb6FF36iBL93`. Если это UID именно вашего аккаунта, правило
в целом соответствует задаче: владелец читает и изменяет свои документы и
подколлекции, а запросы без входа и запросы других UID запрещены. Но файл сам
по себе не доказывает, что эти правила опубликованы в проекте
`dwarfs-life-app` и базе `(default)`; это можно подтвердить только в Firebase
Console/CLI.

Вариант для личного аккаунта с вашим текущим UID (если он подтверждён в UI):

```firestore
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isOwner(uid) {
      return request.auth != null
        && request.auth.uid == uid
        && request.auth.uid == '2fANEOpUDmczCaVAhb6FF36iBL93';
    }

    match /workspaces/{uid} {
      allow read, write: if isOwner(uid);

      match /{document=**} {
        allow read, write: if isOwner(uid);
      }
    }
  }
}
```

Это намеренно даёт владельцу полный CRUD-доступ ко всем документам внутри его
workspace. Для текущей модели приложения, где клиент напрямую пишет Firestore
REST, такая широкая запись нужна протоколу. Она не проверяет форму payload,
ограничения размера, допустимые поля или переходы ревизий. Для одиночного
владельца основной барьер — аутентификация UID; при добавлении пользователей
или недоверенных клиентов потребуется строгая валидация полей/схемы или
серверный слой. `allow ...: if false` в catch-all блоке не усиливает deny:
перекрывающиеся `allow` правила объединяются по OR, поэтому блок избыточен,
хотя текущие условия владельца остаются ограничительными. Это поведение
описано в [официальной документации Firebase о перекрывающихся match]
(https://firebase.google.com/docs/firestore/security/rules-structure).

Заменять UID следует только на значение, показанное приложением после входа в
тот аккаунт, который должен владеть данными. Не публиковать это значение как
секрет не требуется: UID — идентификатор, а не credential. Важно не публиковать
правило вида `request.auth != null` без сверки UID: тогда любой вошедший
Firebase-пользователь получит доступ к workspace, если сможет угадать его ID.

### Остаточные замечания

#### P1 — Переход offline edits при смене epoch всё ещё уничтожает очередь

`acceptEpochSnapshot()` явно предупреждает пользователя, затем очищает
сущности и outbox перед pull нового снимка ([sync_engine.dart](lib/sync/sync_engine.dart)).
Это уже не скрытая автоматическая потеря, но операция необратима и в коде нет
экспорта/резервной копии/отмены. Если пользователь подтверждает не понимая,
что именно будет потеряно, локальные несинхронизированные изменения исчезают.

**Как улучшить:** перед подтверждением показывать число pending-операций и
понятное последствие; предложить экспорт/локальную копию или запись изменений
в отдельную конфликтную область. Проверить транзакционность очистки и поведение
при ошибке pull после очистки.

#### P1 — `initialMerge()` может затереть облачную версию локальной

Первое объединение сначала записывает локальные сущности в outbox, затем
отправляет их, а уже после этого pull читает облако. Если обе стороны уже
содержат один entity ID с разными значениями, локальный push может заменить
облачный документ прежде, чем трёхсторонний merge увидит прежнюю облачную
версию. Сценарий особенно важен при повторном входе/переустановке и не
проверяется текущими unit-тестами merge.

**Как улучшить:** сначала получить серверные документы и базовые ревизии,
затем объединить локальные/облачные записи, и только результат отправить.
Проверить отдельно одинаковые и разные entity ID и конфликт одного ID.

#### P1 — После commit локальная очистка outbox не атомарна с подтверждением базы

В `_pushChunk()` серверный commit выполняется до локальных операций очистки
outbox и обновления `sync_base`. Сбой приложения между успешным commit и
локальным подтверждением оставляет старую операцию в outbox; повторная
отправка может перезаписать более новую облачную версию или породить неверное
слияние. Идемпотентный ID операции хранится локально, но не записывается в
облако как проверяемый маркер обработки.

**Как улучшить:** хранить серверный `operation_id`/revision и обеспечивать
идемпотентную обработку; на повторе перечитывать документ и сравнивать
ревизию/базу, прежде чем повторно применять payload.

#### P2 — Курсор push может перескочить через входящие изменения

После push код устанавливает локальный `commit_cursor` в `seq`, который
принадлежит общему workspace-счётчику и назначен отправленному пакету. Если
между локальным pull и push на сервере появились чужие commits с меньшими или
равными номерами, курсор может пропустить их. Надёжнее хранить подтверждённые
собственные commit IDs/диапазоны или выполнять pull до продвижения курсора с
учётом того, какие серверные последовательности действительно применены.

**Как улучшить:** проверить чередование двух устройств: A читает seq N, B
пишет N+1, затем A пишет N+2 и сразу продвигает cursor. Убедиться, что B-изменение
не теряется при всех последовательностях транзакций.

#### P2 — Правила Firestore не ограничивают поля документов

Правило разрешает владельцу любые поля и любые изменения внутри workspace.
Это не даёт чужому UID доступ, но ошибочный или модифицированный клиент может
перезаписать `active_epoch`, `commit_seq`, тип сущности и payload. Если защита
от случайного повреждения важна, добавьте проверки `request.resource.data`
для workspace и entity-документов: разрешённые ключи, типы полей,
неотрицательные последовательности, неизменность/валидность epoch. Учтите,
что строгая проверка согласованности документов в batch/transaction усложняет
правила; протестируйте полный REST-запрос в Firestore Emulator.

#### P2 — OAuth secret всё ещё лежит в клиенте; nonce JWT не валидируется

`desktopClientSecret` по-прежнему зашит в `firebase_config.dart` и передаётся
из приложения. Перемещение строки из одного файла в другой не сделает её
секретной. Desktop OAuth-клиент следует считать публичным; подтвердить в
Google Cloud Console, что тип клиента именно Desktop app и что flow работает
без полагания на конфиденциальность строки. Desktop `_verifyNonce()` читает
payload id token, но не проверяет подпись, `iss`, `aud` и `exp`. Это явно
обозначено как ограничение в docs; для production лучше поручить проверку
проверенной библиотеке или проверять JWT по JWKS Google.

#### P2 — UI-состояние после исключения может не показывать фактический статус

Основная sync-ошибка теперь сбрасывает `permissionDenied` в начале попытки и
в успехе, что исправляет прежнее замечание. Но `epochSwitchRequired` и
отдельные статусы зависят от каждой ветки обновления; нужно убедиться, что
после не-Firebase исключения и при повторе предыдущий флаг epoch/mismatch не
остаётся в UI. В частности, `copyWith` сохраняет не переданные bool-поля.

### Разметка и UX

Проверил структуру основных экранов и сценарии настроек/корзины/диагностики.
Главное UX-замечание связано не с визуальной стилистикой, а с потенциально
необратимым подтверждением смены epoch: перед очисткой надо показать конкретное
количество ожидающих операций и дать способ сохранить копию. В настройках
пользователь видит UID, что помогает сопоставить аккаунт с правилами. Ручная
диагностика полезна, но обычный экран синхронизации должен показывать
человеко-понятную причину и следующий шаг, не требуя открывать логи.

### Мёртвый код и «заплатки»

- `allow read, write: if false` для catch-all — декоративное правило: запрет
  по умолчанию уже действует, а перекрывающиеся разрешения складываются по
  OR. Удалить блок или оставить комментарий с корректным смыслом.
- `authDomain` в `FirebaseConfig` не используется в найденном Dart-коде;
  проверить поиском по всему репозиторию перед удалением.
- В Android Gradle остался шаблонный TODO о замене `applicationId`; убедиться,
  что `com.hyrladzhyu.life.app` — окончательный package ID и OAuth/Firebase
  конфигурации соответствуют release signing certificate.
- В `TrashService` есть комментарий, случайно склеенный с декларацией
  `watchTrashedNotes()`; исправить комментарий, чтобы не вводить в заблуждение.
- `docs/cloud-setup.md` помечает конфигурацию как проверенную на двух
  устройствах. Это утверждение нельзя подтвердить локальным исходным кодом;
  хранить рядом дату/сценарии проверки или описывать документ как инструкцию.

### Какие проверки нужны перед доверием синхронизации

В репозитории есть unit-тесты доменных функций и новый тест статуса, но
проверка Firestore Rules и протокола двух клиентов не подтверждается ими.
Нужно прогнать Emulator Suite: гость deny; ваш UID на собственном workspace
allow; другой UID deny; доступ к любой вложенной коллекции собственного
workspace allow; данные вне workspace deny. Затем интеграционные сценарии:
первый merge с коллизией ID, конкурентные commits двух устройств, падение
между cloud commit и локальным ack, очистка корзины на офлайн-устройстве и
подтверждённый epoch switch при непустом outbox.

В этом повторном проходе тесты и Flutter analyzer не запускались; выводы
сделаны по текущим файлам. Проверить опубликованную конфигурацию Firebase и
правила из локальной среды невозможно.

## Наиболее важные замечания

### P1 — Доступ к Firestore привязан к конкретному UID, а инструкция не соответствует правилам

В [firestore.rules](firestore.rules) `isOwner` допускает запрос только если UID аутентифицированного пользователя равен UID workspace и одновременно равен жёстко зашитому `2fANEOpUDmczCaVAhb6FF36iBL93`. Между тем [docs/cloud-setup.md](docs/cloud-setup.md) предлагает заменить `OWNER_UID_PLACEHOLDER`, которого в актуальном файле уже нет. Если UID из настроек приложения отличается от зашитого либо в Firebase Console опубликована другая версия правил/правила другого проекта, чтение workspace в начале синхронизации будет отклонено с 403.

**Исправление:** сверить UID из настроек с опубликованными правилами и убедиться, что правила опубликованы в проекте `dwarfs-life-app`. Обновить инструкцию: описать замену фактического значения либо безопасную конфигурацию владельца. Не удалять проверку владельца без разработки отдельной модели доступа.

### P1 — Проверка локального аккаунта происходит после сетевого запроса

`syncNow()` вызывает `_ensureWorkspace(uid)` до `_pushOutbox()`, а сравнение сохранённого `sync.workspace_uid` с текущим UID расположено внутри `_pushOutbox()`. При смене аккаунта приложение уже успевает обратиться к workspace нового UID; правила владельца могут вернуть 403 до защитной проверки. Кроме того, `_pushOutbox()` при mismatch только записывает статус и возвращает управление, после чего `syncNow()` продолжает pull как будто синхронизация прошла.

**Исправление:** проверять привязку локальных данных к аккаунту до любого обращения к сети. При несовпадении завершать `syncNow()` явным результатом ошибки, не выполнять pull и не сообщать об успешной синхронизации.

### P1 — Push игнорирует активный epoch workspace

В `_entityWrite()` epoch всегда равен `1`. Pull, напротив, читает `active_epoch` из workspace и загружает документы активного epoch. После смены epoch записи продолжат отправляться в старую коллекцию, а другие устройства их не увидят.

**Исправление:** читать активный epoch вместе со счётчиком workspace и передавать его в формирование всех записей push. Добавить проверки протокола смены epoch.

### P1 — Полная пересинхронизация удаляет локальные данные и outbox

`_fullResync()` очищает таблицы сущностей, `outbox_entries` и `sync_base`, прежде чем загрузить новый epoch. Это намеренно описано в комментарии как отбрасывание локальных изменений, но в коде нет предварительной проверки, что локальные операции уже отправлены или что пользователь согласен потерять их. При наличии ожидающих изменений это может привести к безвозвратной потере данных.

**Исправление:** до очистки проверять outbox и локальные несинхронизированные ревизии. Сохранять их в отдельный снимок/конфликт либо останавливать операцию и требовать явного решения; не стирать очередь молча.

### P1 — Восстановление из корзины не везде попадает в outbox

`TrashService.restoreNote()` и `restoreFolder()` меняют локальную запись, но сервис не получает `OutboxLedger` и не ставит восстановленную сущность в очередь. Изменение может не попасть на другие устройства. В отличие от них, восстановление списка и ветки задач реализовано в соответствующих сервисах с записью в outbox.

**Исправление:** включить запись upsert в outbox в ту же транзакцию, что и восстановление. Проверить аналогично все операции, меняющие синхронизируемые данные.

### P1 — Физическое удаление создаёт только локальный маркер

`TrashService.purgeExpired()` записывает в `deletion_markers` и удаляет локальные строки, но не добавляет соответствующие удаления в `outbox_entries`. По текущему коду синхронизация отправляет outbox, а `deletion_markers` не участвуют в push/pull. Удалённые локально сущности могут остаться в облаке или появиться снова на другом устройстве.

**Исправление:** определить единый протокол синхронизации компактных tombstone-маркеров и включить их в outbox/облачный обмен; согласовать срок хранения и поведение давно отключённых устройств.

### P2 — Ошибки REST Firestore разбираются в неверном формате

В `_check()` ответ ошибки распознаётся только когда JSON — непустой список. Обычный REST-ответ ошибки — объект с полем `error`; в этом случае приложение сохраняет сырое тело, не извлекает диагностическое сообщение и оставляет `permissionDenied == false`, даже при HTTP 403. Это мешает понять причину отказа в UI.

**Исправление:** разобрать объект `{"error": ...}` и отдельно поддержать список ответов `runQuery`; классифицировать запрет по HTTP-коду и/или `error.status`, сохраняя исходный HTTP-код и сообщение.

### P2 — Статус ошибки может остаться после успешной синхронизации

`SyncStatus.copyWith()` использует `permissionDenied ?? this.permissionDenied` и аналогичное выражение для `workspaceMismatch`. В успешном пути эти флаги явно не сбрасываются, поэтому после исправления доступа UI может продолжать показывать старый статус.

**Исправление:** сделать сброс состояния явным (например, sentinel-параметрами для nullable значений или конструктором успешного состояния) и сбрасывать оба флага при новой попытке/успехе.

### P2 — Desktop OAuth secret включён в исходники и бинарник

`desktopClientSecret` хранится в `firebase_config.dart` и отправляется при обмене кода. Комментарий одновременно называет desktop-клиент публичным и утверждает, что секрет можно поставлять в приложении. Секрет, встроенный в распространяемый клиент, не является секретом.

**Исправление:** использовать корректный для установленного приложения OAuth flow с PKCE и без конфиденциального секрета, сверить тип OAuth-клиента в Google Cloud. Если значение считалось приватным, отозвать/перевыпустить его. Firebase API key сам по себе предназначен для клиентской конфигурации, но его ограничения также следует настроить в Google Cloud.

## Дополнительные риски

- **Гонки при первом создании workspace.** Два клиента могут одновременно получить 404 и оба попытаться создать workspace с `exists:false`. Один commit проиграет; код `_ensureWorkspace()` не повторяет чтение/создание при конфликте. Обработать конфликт как ожидаемую гонку: перечитать документ и продолжить.
- **Ошибки входа могут терять исходный HTTP-ответ.** В `signInWithGoogleIdToken()` и `refreshIdToken()` JSON приводится к ожидаемой карте до проверки статуса и формы ответа. Не-JSON или неожиданная структура дадут ошибку преобразования вместо полезного сетевого сообщения. Добавить безопасный разбор тела и единый обработчик HTTP-ошибок.
- **Настройки устройства хранят JSON-строки, но API возвращает сырую строку.** Проверка workspace UID в коде компенсирует это сравнением с `"$uid"`, но такой контракт хрупкий и неочевидный. Лучше декодировать JSON в `SettingsService` или использовать типизированный метод для UID.
- **OAuth nonce проверяется только разбором payload.** В desktop flow `_verifyNonce()` декодирует JWT и сравнивает nonce, но не проверяет подпись, issuer, audience и срок действия. Для полноценной проверки использовать проверенный OAuth/Firebase SDK либо валидировать JWT по официальным ключам провайдера.
- **Комментарии и документация местами расходятся с реализацией.** Например, правила синхронизации, epoch и восстановление из корзины описаны как завершённые, но путь данных неполный. Документировать фактические ограничения и добавлять тесты на целые сценарии, а не только чистые функции.

## Что сделано хорошо

- Слои `domain`, `data`, `sync`, `cloud` и `ui` в целом разделены.
- Локальная SQLite остаётся рабочим хранилищем, а outbox в большинстве сервисных мутаций записывается вместе с изменением в транзакции.
- Данные OAuth-токенов на Android/Windows хранятся через платформенные защищённые механизмы.
- Поиск использует SQL-параметры и безопасно готовит ввод для FTS.
- Есть тесты доменной логики сроков, сортировки, маппинга и слияния.

## Рекомендуемый порядок исправлений

1. Сверить UID и опубликованные Firestore Rules; исправить инструкцию и обработку 403.
2. Перенести проверку аккаунта перед сетевыми запросами и сделать mismatch причиной остановки.
3. Исправить восстановление/очистку корзины и протокол tombstone, чтобы удаления и восстановления синхронизировались.

5. Исправить сброс статусов, диагностику REST и OAuth flow.
6. После изменений проверить сценарии двух устройств, смены аккаунта, офлайна, восстановления и epoch; добавить тесты на эти сценарии.

## Итог

Проект не выглядит неструктурированным: в нём есть хорошая локальная основа и отдельные качественные доменные части. Низкая оценка связана прежде всего с незрелостью протокола синхронизации и отсутствием сквозной защиты от потери данных. Главный кандидат на текущий 403 — несоответствие UID в опубликованных правилах Firebase и UID активной сессии; детали ответа сейчас выводятся недостаточно надёжно.
